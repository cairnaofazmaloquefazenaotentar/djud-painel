# Design Handoff

Turn design specs into engineering commands that devs can execute without asking questions.

## Overview

This skill reads a design SPEC (generated by `design-spec-evolution`) and produces self-contained engineering prompts for each feature, fix, or improvement identified. Each prompt follows a standardized 5-section format that includes full system context, architecture rules, specific mission, task constraints, and expected output — so the dev (or AI agent) can execute immediately.

The goal: zero back-and-forth between design and engineering. The SPEC has the "what" and "why" — this skill generates the "how."

## When to Use

- After generating a design spec (v1, v2, etc.) — create prompts for identified issues
- During sprint planning — turn SPEC backlog items into executable tasks
- When onboarding a new dev — give them full-context prompts instead of vague tickets
- When using AI coding assistants — prompts are optimized for Claude, Cursor, Copilot
- After design review — generate fix prompts for any Critical/Important findings

## Process

### 1. Load the SPEC

Read the current version of `[system]-spec.v[N].md` from `_spec-design/`. Extract:

- **System context:** name, stack, platform, audience
- **Architecture rules:** design tokens, component patterns, constraints
- **Backlog items:** problems/opportunities from heuristic analysis
- **Design tokens:** colors, typography, spacing (for code accuracy)

### 2. Prioritize Items

From the SPEC's engineering backlog, organize by priority:

- **High:** Heuristic score ≤ 4, or Critical finding from design review
- **Medium:** Heuristic score = 5, or Important finding
- **Low:** Heuristic score ≥ 7 but with minor opportunities

### 3. Generate Engineering Prompts

For each item, generate a prompt using the 5-section template from `references/engineering-prompt-template.md`.

**Key rules for prompt generation:**

- Pull system context directly from SPEC (never make it up)
- Architecture rules come from SPEC constraints + design tokens
- Mission is specific and scoped (one problem per prompt)
- Task rules reference specific SPEC sections (page, component, behavior)
- Expected output is concrete (file names, component names, test files)

### 4. Validate Prompts

Each prompt must pass these checks:

- [ ] Self-contained — dev can execute without reading the SPEC
- [ ] Specific — references exact components, pages, behaviors
- [ ] Scoped — one clear mission per prompt (not "fix everything")
- [ ] Testable — expected output includes verification criteria
- [ ] Context-rich — includes stack, tokens, constraints from SPEC

### 5. Distribute

Output prompts as individual code blocks within the SPEC or as separate files:

```
_spec-design/
├── delivery-checkout-spec.v1.md
└── prompts/
    ├── 01-fix-error-handling.md
    ├── 02-add-confirmation-drawer.md
    └── 03-improve-accessibility.md
```

## Common Rationalizations

| Rationalization | Reality |
|:--|:--|
| "Devs can read the SPEC themselves" | They can, but won't extract the same priorities you would. Prompts encode your design intent. |
| "AI prompts are too rigid" | The 5-section format is a starting point. Devs adapt as needed, but the baseline is complete. |
| "This creates too many files" | One prompt per problem keeps scope clear. A monolithic "fix everything" prompt produces monolithic, untestable changes. |
| "I'll just explain in standup" | Verbal handoffs lose detail. Written prompts are permanent, shareable, and auditable. |

## Red Flags

- **No SPEC exists** — generate a SPEC first using `design-spec-evolution`, then handoff
- **SPEC has no heuristic analysis** — without scored issues, there's nothing to generate prompts for
- **Prompt references components that don't exist yet** — check that the SPEC reflects current state
- **Single prompt tries to fix 5+ issues** — split into focused, single-mission prompts

## Verification

- [ ] Every prompt is self-contained (no external context needed)
- [ ] Every prompt references specific SPEC sections
- [ ] Architecture rules match the project's actual stack
- [ ] Expected output includes file names and test expectations
- [ ] Prompts are prioritized (Critical → Important → Nice-to-have)
